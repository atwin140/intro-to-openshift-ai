# OAI-00A — Configure a fresh checkout

Applicability: public template derived from the tested OpenShift 4.22 / AI 3.5 lab. Required role: cluster administrator for discovery and preparation; project administrator after Stage 3. This module changes local files only. A one-GPU rendering is supplied; it has not been run end to end on a new cluster.

## Objective and prerequisites

Turn the example configuration into a reviewed configuration for your cluster before deployment. Keep a separate working copy for each training cluster. Never commit credentials or raw inventory. Run commands from the repository root, unless a module explicitly says otherwise. You need `oc`, Python 3, Bash, curl, jq, internet access, working cluster authentication and registry access for the pinned Red Hat images. The chat model download is public; registry authentication is a separate prerequisite.

First complete Stage 0 discovery. Do not install the pinned operator bundles until the catalog and version compatibility are verified. The source records previously tested versions; it does not guarantee that those bundles remain available in every catalog. OpenShift AI must already be installed as described by the original prerequisites.

## Configure local values

The `lab` overlays contain example settings and must be edited before use. The numeric example filesystem group is not a portable security allocation. Read the real allocation after Stage 3 creates the project, then update every applicable patch. For a one-worker cluster, use the same discovered hostname for both storage-test patches; this tests detach/remount and persistence on one worker, not cross-worker relocation.

| Value | Complete files to edit |
| --- | --- |
| First GPU worker hostname | `platform/gpu/validation/overlays/lab/worker-01.json`, `platform/storage-check/write/overlays/lab/placement-security.json`, `deploy/download/overlays/lab/settings.yaml`, `deploy/overlays/lab-model/model-settings-patch.yaml` |
| Second worker, or the first worker again for single-worker storage checks | `platform/storage-check/read/overlays/lab/placement-security.json`; edit `platform/gpu/validation/overlays/lab/worker-02.json` only for two-GPU validation |
| StorageClass | `platform/storage-check/overlays/lab/storage.yaml`, `deploy/storage/overlays/lab/storage.yaml`, `deploy/overlays/lab-model/storage.yaml` |
| Project's allocated fsGroup | Both storage-test security patches, model download settings and model-serving settings listed above |
| Intended project user | `platform/project-access/overlays/lab/identity.yaml` |
| Chat hostname and matching HTTPS origin | Both values in `deploy/overlays/lab/chatbot-settings.yaml` |
| Expected API address and model Route hostname for checks | `checks/project-permissions.py` and `checks/model-route.py` |
| Chat URL for checks | `BASE` in `checks/chatbot.py` and `checks/chat-context.py` |

The namespace remains `intro-openshift-ai` throughout this guide. Use that same name on each separate cluster. Model Route hostnames are generated by the installed serving platform; inspect the created Route and update the test's expected hostname before sending credentials. Keep TLS validation enabled. Example domains use `example.com` and are not working endpoints.

The optional image extension has separate worker, storage, fsGroup, endpoint and API values under `image-generation/`. Omit it from the initial one-GPU lab. To run it later, stop the chatbot model deliberately at a separate checkpoint so both do not request the same whole GPU.

## Single-GPU Stage 1 alternative

Use this overlay instead of the two-worker validation overlay in Stage 1:

```bash
oc kustomize platform/gpu/validation/overlays/single-gpu
oc apply -k platform/gpu/validation/overlays/single-gpu
oc wait --for=condition=Complete job/cuda-vectoradd-01 -n intro-ai-gpu-checks --timeout=300s
oc logs -n intro-ai-gpu-checks job/cuda-vectoradd-01
oc get pods -n intro-ai-gpu-checks -o wide
```

Expect one Job, one GPU request, the intended worker and `Test PASSED`. Preserve evidence locally and clean up with the same single-GPU overlay. Do not run the two-worker overlay as well. Interpret later “both workers” checkpoints as “every GPU worker in this cluster”; a one-worker run must not be recorded as a two-worker test.

## Verify before applying

```bash
python3 checks/review-walkthrough.py
python3 checks/test-reset-lab.py
oc whoami --show-server
oc whoami
```

Inspect each rendered overlay and run the stage's server dry run once its prerequisite APIs exist. Structural checks do not validate admission, image pulls, storage attachment, model quality or GPU execution. Inspect the cluster through the console as described in each stage; do not deploy the same resources twice.

## Completion checkpoint, failures and rollback

Record selected versions, node(s), storage class, cluster identity and participant identity in private notes. Stop if credentials, registry access, compatibility or storage prerequisites fail. Do not resolve failures by disabling TLS, forcing finalizers, or granting project participants cluster-admin.

If local settings are wrong, correct the files before applying. If resources were deployed, use the relevant stage's cleanup or the guarded reset module. Keep source configuration changes under review; a reset does not restore lost data. Repeat the filesystem-group check after recreating the project.
